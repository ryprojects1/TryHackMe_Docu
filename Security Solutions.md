## 📂 Log Sources

Logs basically come from two places: **inside a host** or **between hosts on the network**.

### 1. Host-Centric Log Sources

Events that happen *on* or *related to* a host.

**Generated by:** Windows, Linux, servers, etc.

| Example | What it tells you |
|---|---|
| User accessing a file | Who touched what |
| Authentication attempt | Login successes / failures |
| Process execution | What programs ran |
| Registry key/value add/edit/delete | Persistence, config tampering |
| PowerShell execution | Scripted activity (attackers love this) |

### 2. Network-Centric Log Sources

Generated when hosts talk to each other or reach out to the internet.

**Generated by:** firewalls, IDS/IPS, routers, etc.

| Example |
|---|
| SSH connections |
| File access via FTP |
| Web traffic |
| VPN access to company resources |
| Network file sharing activity |

## 😩 Why Manual Log Analysis Doesn't Scale

Without a SIEM, you hit these problems pretty quickly:

| Problem | Why it hurts |
|---|---|
| **Numerous log sources** | Hundreds of events per second, spread across loads of devices. Checking them one by one during an incident is painful. |
| **No centralisation** | Logs stay on the machine that made them, so you have to SSH/RDP into each one. Slow and wastes time mid-investigation. |
| **Limited context** | One log on its own rarely tells the full story. A normal-looking file access might actually be part of **lateral movement** once you correlate it with other sources. |
| **Limited analysis** | Humans can't manually read every log from every device. Important stuff *will* get missed. |
| **Format issues** | Every source logs in a different format, and you'd need to know all of them. |

## ⚙️ Core SIEM Features

A SIEM fixes the problems above *and* adds extra capability on top.

### 🗃️ Centralised Log Collection
Pulls logs from all sources (endpoints, servers, firewalls...) into **one place** via lightweight agents or APIs. No more hopping between machines.

### 🔧 Normalisation of Logs
A Windows log looks nothing like a Linux log, so the SIEM sorts that out:

- **Parsing** = breaking a log down into individual fields
- **Normalisation** = converting logs from all sources into **one consistent format**

### 🔗 Correlation of Logs
Finds relationships between logs from *different* sources to spot malicious patterns.

**Example** (all within 5 minutes):

```
1. Haris logs in via VPN from an IP he's never used before
2. Haris accesses documents on a shared drive
3. Haris executes a PowerShell script
4. The system makes an outbound network connection
```

On their own, each of these looks fine. Put together, it looks like **compromised credentials → data access → script execution → possible exfiltration / C2**.

### 🚨 Real-Time Alerting
- Detects malicious activity using **rules**
- Comes with default rules, and analysts write custom ones to improve detection over time
- When a rule's conditions are met → **alert fires** → analyst gets notified and investigates inside the SIEM

### 📊 Dashboards & Reporting
Dashboards are the **most important part** of a SIEM. They turn normalised data into actionable insights. Default dashboards are included, and you can build custom ones.

Typical dashboard info:
- Alert highlights
- System notifications
- Health alerts
- Failed login attempts
- Events ingested count
- Rules triggered
- Top domains visited

## 📥 Log Ingestion Methods

How logs actually get into the SIEM:

| Method | How it works |
|---|---|
| **Agent / Forwarder** | Lightweight tool installed on the endpoint that captures and sends important logs to the SIEM server (Splunk calls it a *forwarder*). |
| **Syslog** | Widely used protocol for sending real-time data from systems like web servers and databases to a central destination. |
| **Manual Upload** | Some SIEMs (Splunk, ELK...) let you ingest offline data for quick analysis. It still gets normalised. |
| **Port-Forwarding** | SIEM listens on a port, and endpoints forward their data to it. |

## 📝 Creating Detection Rules

Rules are basically **IF [conditions] THEN [alert]**.

### Use Case 1: Event Log Cleared

Attackers often **clear logs** post-exploitation to cover their tracks. Windows logs **Event ID 104** whenever someone clears event logs.

```text
Rule:
IF   LogSource = WinEventLog
AND  EventID   = 104
THEN Trigger Alert → "Event Log Cleared"
```

### Use Case 2: `whoami` Execution

Attackers often run `whoami` after exploitation / privilege escalation to check who they are on the box.

Useful fields:
- **Log source:** where the event is captured (WinEventLog)
- **Event ID:** `4688`, which means process execution
- **NewProcessName:** the process that ran, in this case containing `whoami`

```text
Rule:
IF   LogSource      = WinEventLog
AND  EventCode      = 4688
AND  NewProcessName CONTAINS "whoami"
THEN Trigger Alert → "WHOAMI Command Execution DETECTED"
```

### 🔑 Event IDs to remember

| Event ID | Meaning |
|---|---|
| `104` | Event log cleared |
| `4688` | New process created |

## 🔍 Alert Investigation

Analysts spend most of their time on **dashboards**. When an alert fires:

1. Examine the **events/flows** linked to the alert
2. Check the **rule** and see which conditions were met
3. Decide: **True Positive** or **False Positive**?

```text
                 ┌─────────────┐
                 │ Alert fires │
                 └──────┬──────┘
                        │
              Investigate events + rule
                        │
          ┌─────────────┴─────────────┐
          ▼                           ▼
   False Positive               True Positive
          │                           │
  Tune the rule to stop     Investigate further
  it happening again                  │
                            Contact asset owner
                                      │
                         Suspicious activity confirmed?
                                      │
                        ┌─────────────┴─────────────┐
                        ▼                           ▼
                Isolate infected host      Block suspicious IP
```

## firewall fundamental
A firewall is designed to inspect a network's or digital device’s incoming and outgoing traffic. The goal is the same as for the security guard sitting outside a building: not letting any unauthorized visitor enter a system or a network
Stateless Firewall
This type of firewall operates on layer 3 and layer 4 of the OSI model and works solely by filtering the data based on predetermined rules without taking note of the state of the previous connections. This means it will match every packet with the rules regardless of whether it is part of a legitimate connection. It maintains no information on the state of the previous connections to make decisions for future packets. Due to this, these firewalls can process the packets quickly. However, they cannot apply complex policies to the data based on its relationship with the previous connections. 
Stateful Firewall
Unlike stateless firewalls, this type of firewall goes beyond filtering packets by predetermined rules. It also keeps track of previous connections and stores them in a state table. This adds another layer of security by inspecting the packets based on their history with connections
Proxy Firewall
The problem with previous firewalls was their inability to inspect the contents of a packet. Proxy firewalls, or application-level gateways, act as intermediaries between the private network and the Internet and operate on the OSI model’s layer 7. They inspect the content of all packets as well. The requests made by users in a network are forwarded by this proxy after inspection and masking them with their own IP address to provide anonymity for the internal IP addresses.
Next-Generation Firewall (NGFW)
This is the most advanced type of firewall that operates from layer 3 to layer 7 of the OSI model, offering deep packet inspection and other functionalities that enhance the security of incoming and outgoing network traffic. It has an intrusion prevention system that blocks malicious activities in real time. It offers heuristic analysis by analyzing the patterns of attacks and blocking them instantly before reaching the network.

- The basic components of a firewall’s rule are described below:

Source address: The machine’s IP address that would originate the traffic.
Destination address: The machine’s IP address that would receive the data.
Port: The port number for the traffic.
Protocol: The protocol that would be used during the communication.
Action: This defines the action that would be taken upon identifying any traffic of this particular nature.
Direction: This field defines the rule’s applicability to incoming or outgoing traffic.
Inbound Rules
Rules are categorized as inbound rules when they are meant to be applied to incoming traffic only. For example, you might allow incoming HTTP traffic (port 80) on your web server.

Outbound Rules
These rules are made for outgoing traffic only. For example, blocking all outgoing SMTP traffic (port 25) from all the devices except the mail server.

Forward Rules
Forwarding rules are created to forward specific traffic inside the network. For example, a forwarding rule can be created to forward the incoming HTTP (port 80) traffic to the web server located in your network.
Netfilter
Netfilter is the framework inside the Linux OS with core firewall functionalities, including packet filtering, NAT, and connection tracking. This framework serves as the foundation for various firewall utilities available in Linux to control network traffic. Some common firewall utilities that utilize this framework are listed below:

iptables: This is the most widely used utility in many Linux distributions. It uses the Netfilter framework that provides various functionalities to control network traffic.
nftables: It is a successor to the “iptables” utility, with enhanced packet filtering and NAT capabilities. It is also based on the Netfilter framework.
firewalld: This utility also operates on the Netfilter framework and has predefined rule sets. It works differently from the others and comes with different pre-built network zone configurations.
ufw 
ufw (Uncomplicated Firewall), as the name says, eliminates the complications of making rules in a complex syntax in “iptables”(or its successor) by giving you an easier interface. It is more beginner-friendly. Basically, whatever rules you need in “iptables”, you can define them with some easy commands via ufw, which would then be configuring your desired rules in “iptables”.
